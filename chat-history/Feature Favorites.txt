  What I found

  API
  - GET /pokemon/{id} returns id, name, types, sprites and more, so it's a large
    response just to get a name.
  - Alternate forms work: 10001 returns deoxys-attack, and its image loads.
    Favorites can therefore be any of the 1351 entries.
  - An unknown ID returns 404 (99999).
  - The API has no endpoint for fetching several Pokémon at once. Because SQLite
    stores only the ID, each favorite needs its own request to get its name, so
    30 favorites means 30 requests.

  Existing app
  - Favorites tab: src/app/(tabs)/favorites.tsx is still an empty <View />.
  - Reusable parts: PokemonCardList and PokemonCard only need id and name, so
    the grid can be reused. ListStates covers the spinner, error and message
    states.

    key uses a string ID.
  - Detail heart: it's visual-only today, and the detail page spec
    (specs/features/detail%20page.md) leaves the working heart to this feature.
    That spec also has an untested criterion: Detail opened from Favorites must
    go back to Favorites.

  - Offline: the query client uses default settings, so unused data leaves the

  Two choices for you

  1. Where does the title go? The spec says "same style and position as All

  - A (recommended): A pure function toFavoriteIds sorts by number and removes

  - B: Mock expo-sqlite. This only proves which SQL text was sent, not how it

  Approach

  - Data: the favorite IDs live in one SQLite table, read through the query
    ['favorites'], so the heart and the Favorites page always agree. Each
    favorite gets its own /pokemon/{id} query, sharing its cache with Detail.
  - Database: I'd open it with openDatabaseAsync rather than SQLiteProvider, so
    a failed open becomes a normal error with a working Retry. The SDK 58 docs
    confirm expo-sqlite is included in Expo Go and needs no config plugin for
    this.
  - States: a pure function in src/lib/favorites.ts works out the card and page
    states, so they can be unit tested. A favorite counts as loaded whenever it
    has data, which is how cached names survive offline.
  - Heart: it writes to SQLite and waits for ['favorites'] to reload before it
    changes. Taps during a save are ignored, and a failed save shows the native
    alert.
  - Back from Detail: this needs no new code, because router.push and
    router.replace already return to the tab you came from.
  - Web: not supported for this feature, because expo-sqlite needs extra setup
    there and the app targets Expo Go.

  How the code works, in plain language

  - Saving (db/favorites.ts (src/db/favorites.ts)): the database holds one table
    with one column, the Pokémon ID. Making that column the primary key means
    the same ID can't be stored twice. The database opens once and is reused. If
    opening fails, that attempt is forgotten, so Retry tries again.
  - One source of truth (useFavorites.ts (src/hooks/useFavorites.ts)): the heart
    and the Favorites page both read the same ['favorites'] query, so they
    can't disagree. After a save, invalidateQueries tells TanStack Query to
    reload that list, and both update together.
  - Why the heart waits: it has no state of its own and only shows what's saved.
    A failed save changes nothing, so there's nothing to undo. You just get the
    alert.
  - Loading every favorite: only IDs are stored, so names come from the API.
    useQueries runs one request per ID, which lets each card fill in by itself.
    Favorites and Detail use the same query key, so opening a favorite on Detail
    reuses the data already fetched.
  - Card states (lib/favorites.ts (src/lib/favorites.ts)): no name and still
    running means loading, so the card shows only the badge. No name and
    finished means failed, so it shows "Unknown". A name means loaded, even if a
    later refresh failed, which is why cached names survive offline. This is
    plain TypeScript without React, so it's easy to unit test.
  - Page state: the page only decides once no requests are running. If none
    failed it's fine, if some failed it adds the bottom Retry, and if all failed
    it shows the full-page error.
  - Retry: it refetches only the failed queries. A query with no data goes back
    to "pending", so those cards automatically return to badge-only.
