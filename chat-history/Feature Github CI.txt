  How the code works, in plain language

  The workflow file
  - Lines 3-4, when it runs: push with no filter means every push to any branch.
    Branch pushes still show on a PR, because the result is attached to the
    commit.
  - Lines 6-7, access: the workflow can only read the repo, because it needs
    nothing else.
  - Lines 10-12, the job: GitHub starts a fresh Linux machine. The name checks
    matters, because branch protection looks for exactly that name, so renaming
    it would leave every PR waiting forever.
  - Lines 14-18, setup: it downloads your code and installs Node 22.
  - Lines 20-22, install: npm ci installs exactly what's in package-lock.json,
    and fails if that file doesn't match package.json. That's what makes the
    install repeatable.
  - Lines 25, 29, 33, the key condition: normally GitHub stops at the first
    failed step, and a lint error would hide your type errors. This line says
    "run this if the install worked and nobody cancelled the run", so you see
    every problem in one go. Without a working install there's nothing to check,
    so the checks are skipped. The job still fails, so a skipped step can't
    sneak through as a pass.
  - Line 26, --max-warnings 0: ESLint normally only fails on errors. This treats
    a single warning as a failure.

  Branch protection is a GitHub setting, not a file, so you won't find it in the
  repo:
  - The workflow only reports a result. This rule is what acts on it, by
    refusing to change main unless that commit has a passing checks.
  - enforce_admins removes your own bypass as repo owner.

  Why protection came before the final merge: a workflow runs from the branch
  it's on, so it could be tested before reaching main. That let the issue close
  only once everything was built and proven.
