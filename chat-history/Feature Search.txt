> Any reason issue search is #3 and not #2?

● Yes: GitHub uses one shared number sequence for issues and pull requests in a
  repo. Issue #1 was the homepage list, and #2 went to the pull request that
  merged it (the "Merge pull request #2 from Lucas-Light/feature/homepage-list"
  commit in your history). That made #3 the next free number.

  So nothing went wrong, and no number was skipped. If you open a PR for search,
  it will probably become #4, and the next feature issue #5, so the numbers
  won't line up with the feature table's order. That's why the table has its own
  # column alongside the issue numbers.

  How the code works

  - Why the search runs on the phone: PokeAPI can't search by part of a name, so
    the app downloads all 1351 names once (about 93 KB) and filters them
    locally. That's why typing never triggers a request.
  - normalizeSearchQuery: it turns what people type into the format the API
    uses, so MR Mimé  becomes mr-mime. Matching is then just a check for whether
    a name contains that text. This is plain logic with no React in it, which
    makes it easy to unit test.
  - usePokemonSearch: this hook is the brain of the feature. It remembers the
    typed text and whether the bar has been tapped. enabled: listRequested keeps
    the query switched off until that first tap. The query key doesn't include
    the text, so a new letter never starts a new request.
  - Derived state: isSearching and results aren't stored. They're calculated
    from the text on every render, so they can't get out of step with what's in
    the bar. That's also why results appear on their own once a slow fetch
    finishes.
  - The layer trick: the full list is never removed. The results are drawn on
    top of it in an opaque layer, like laying a sheet of paper over a page.
    Because the list stays where it is, it keeps its scroll position with no
    extra code.
  - Keyboard behaviour: keyboardShouldPersistTaps="never" is React Native's rule
    that a tap on a list with the keyboard open only closes the keyboard.
    on-drag closes it when scrolling. The outer Pressable handles taps outside
    the lists.
  - SearchResults: it checks four situations in order: still loading, failed,
    nothing found, or results to show. Only one can be on screen at a time.
